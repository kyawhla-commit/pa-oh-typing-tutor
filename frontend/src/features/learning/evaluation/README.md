# Offline evaluation: accepted Slice 9 baseline and Slice 10 robustness

Run `pnpm learning:evaluate` from the frontend directory. The command uses Vite's installed TypeScript module loader in middleware mode, with HTTP/WebSocket listening and file watching disabled. It writes ignored `.learning-evaluation/evaluation-report.json`, `evaluation-report.md`, `content-samples.md`, and `performance.json`. No production component imports this area. No cloud telemetry, SDK, UI, or planner is added.

## What is evaluated

Explicit version-1 histories cover twelve behavior personas, ten competition cases, 28 progression cases, sixteen controlled-assessment cases, three lifetime-competition histories, and four boundary cases (73 accepted Slice 9 scenarios). Slice 10 retains those histories and adds seven focused overlap/executability histories, for 80 scenarios. Errors are placed at deterministic, evenly distributed production-prepared grapheme/token positions. Fixed, timed and word modes run the actual typing engine, with real insertion/deletion commands and completion boundaries. WPM is controlled through timestamps; accuracy derives from insertion counts rather than a fabricated metric. Some boundary probes deliberately repeat short targets: these are threshold tests, not plausible full lessons.

The simulator invokes production evidence extraction, aggregation, recommendation scoring/overlay, identity, mastery, action, assessment eligibility, variant reservation and generation. It records permitted user-selected actions; unavailable requested actions are explicit. A scenario can select a previously captured recommendation, as the production service permits; this is not an autonomous scheduler that always selects the current top item. Repeated frozen Restart drills reuse the last exercise and ordinal without reserving another exercise; they remain adaptive evidence and cannot create natural mastery. Scope, deferred completion/save independence, reload, version/ordinal identity and abort boundaries additionally use the real learning service. There is no DOM-event simulation in the evaluator.

Hidden record actions describe production stage intent, not an offered capability; candidate audit actions are null when hidden. All visible focused actions have exact verified witnesses. JSON contains compact per-step profile counters, ranked recommendations with original scores, evidence windows/counts/rates and production explanations, every tracked record's level/action/state/gates, generated focus and failure details, and anonymous compact session histories. The score/count data explains ranking without implementing a second scoring policy. Recommendations can overlap: a single mistake can affect a grapheme, direction, adjacent pairs and a word. Slice 10 records the complete eligible list, unchanged raw scores, Unicode overlap signatures, recent error-session provenance, suppression reason, representative and final visible action. Production selection consolidates related training intents without removing profile evidence. Diagnosis checks apply to newly admitted recommendations, while retained records may legitimately have little recent exposure.

Metrics separate detection latency/opportunities, first state steps, mastery latency, top changes, mastery/regression transitions, waiting before offers, offer counts, tracked actionable hidden steps, suppression, and regression steps. `detection=null` is a missing intended category, not proof of no related recommendation. Hidden-step counts exclude targets that were never tracked. The suppression predicate is vacuously true if the intended target never reached mastery; check `masteryStep` and the actual records before interpreting it as observed suppression. Scenario exercise density is the maximum section density; matrix rows separately report whole-exercise and section densities. Offers count snapshots where an explicit action is available, not automatically launched checks or measured user uptake. No single “system accuracy” score is computed.

## Reproducibility and acceptance

All histories use explicit scenario IDs/version/inputs, with no random numbers, timestamps or machine speed in deterministic reports. The same engine-extracted evidence can be replayed independently. Evidence replay compares profiles/mastery records/actions; completed histories cannot reconstruct reservations for exercises that were started but never completed, so this comparison excludes variant cursors. Full scenario determinism also compares reserved variants. Volatile runtime and per-exercise generation time are only in `performance.json`. Ten semantic golden contracts check detection, direction, broad override, natural mastery, drill-only non-mastery, rare-token controlled mastery, failure rollback, regression, maximum-three competition and tiny-sample fallback. The original twenty-two invariants remain; eight additional visibility/executability contracts bring the total to thirty. All have explicit check counts: untested invariants or violations fail the command, as do failed goldens. Tests avoid giant snapshots.

Sensitivity uses thirteen parameter paths with two deliberate neighbors each, baseline plus 26 isolated module graphs. The Node-only loader transforms whitelisted constants in memory; no production file is modified. The same thirteen baseline engine histories are replayed under each configuration. Effects include concrete baseline/neighbor state/action/rank traces. It is a fixed-evidence counterfactual, not a simulation of human responses to changed advice. No defaults are selected automatically. Required counts must fit bounded windows: raising three drill successes to four makes transfer check unreachable with a three-entry training window; checks above five likewise cannot fit the assessment window. These are neighbor configuration warnings, not defects in existing defaults.

## Anonymized real evidence input

`evaluateLearningHistory(unknown)` first calls `validateAnonymousHistory`, then reuses actual profile/mastery/action code. Input is `{version:1, anonymousLearnerId, sessions:[{summary, aggregates, attribution?}]}`. `summary` is the production `SessionSummary`: opaque session/source IDs, source type, mode/completion reason, elapsed time, WPM/accuracy, attempts/mistake/correction/backspace counts. `aggregates` is the bounded production grapheme, directional-substitution, bigram and token aggregate schema. `attribution` is feature-owned adaptive focus/composition/source/check-order metadata. Raw engine results, raw passages, typed buffers, mistake examples, email, authentication and arbitrary extra fields are rejected. Source IDs must be opaque, not URLs/emails. Wall timestamps normalize to zero; array order controls ingestion. Duplicate IDs follow production dedupe behavior.

Input is bounded to 5,000 sessions / 16 MiB. Production storage validators validate counters, arity, source/mode pairs, uniqueness and bounds. The importer adds strict recursive field whitelists, NFC/exact grapheme/token validation, opaque identities and trusted adaptive metadata matching. Custom/quote/unknown sources cannot include token/bigram aggregates. The importer is an offline trust boundary, not proof that a caller has anonymized public-source labels correctly. Public corpus/lesson IDs and token values must be checked against a study allowlist before importing real data. The evaluator has no network input endpoint or upload code.

Repository inspection found fixtures, mock catalog/result data, and analytics code, but no available anonymized actual learner-history dataset. All reported validation is synthetic. An arbitrary Internet dataset would not represent these users and was not used.

## Generator coverage and human review

The full matrix has thirteen foci: two common graphemes, two directional confusions, two pairs, two tokens, accuracy, speed, general, accented grapheme and Myanmar token. Training spans levels 0/1/2 and every ordinal 0–31; ten specific foci also receive attempted controlled assessments. Unsupported checks are counted separately from supported assembly failures; they are never silently counted as successful exercises. This yields 49 groups ×32 =1,568 engineering attempts. Each row reports the actual bounded generation outcome, length, focus occurrences and contexts, densities, repetition and structural flags; failures include production code/reason/attempt count. No extra retry logic is added. Timing is separate.

Diversity counts unique/repeated whole targets, five-token openings, sentence/section fragments and token occurrences within each full cycle. Reuse counts count repeated occurrences, not semantic sentence similarity. Flags use explicit tooling heuristics: punctuation >15%, density above the production composition ceiling, consecutive isolated focus runs, contexts below contract minimum and repeated fragments. These are structural signals, not language-quality judgments. Identical openings across cycles are measured in diversity summaries.

Representative samples include each category, each training level and specific-category assessments at ordinals 0, 7 and 31. The sample artifact is intended for manual reading. English curated passages are drawn from a finite bank and can repeat clauses or openings; progression changes exposure/context balance rather than linguistic sophistication. L0 emphasizes controlled fragments; L1 adds whole contextual phrases; L2 expands ordinary mixed text. Controlled checks put the skill in low-density context but still use a visible focus, so they are not independent psychometric tests. Added punctuation can make occasional clause boundaries feel artificial. Accented and Myanmar content uses exact Unicode in explicitly labeled `fallback-drill` output; neutral English carrier text is not fluent Myanmar/Pa’O instructional content. Do not claim those exercises are natural language lessons. The accepted Slice 9 observations remain unchanged in [FINDINGS.md](FINDINGS.md). Current changes, comparisons, manual review and limitations are documented in [SLICE10.md](SLICE10.md).

## Future analytics readiness (design only)

`analytics.ts` proposes `FutureLearningEvaluationEvent`: consented random study pseudonym + session sequence; mode/source type; approved public source reference; WPM, accuracy, attempts, aggregate errors/corrections and coarse duration; recommendation types; opaque/public weakness references and opportunity/error/session counts; action selected; progression levels; before/after mastery transitions and natural/controlled path. No timestamps, names, emails, auth IDs, typed buffers, raw passages or arbitrary source titles are needed.

Readiness checklist:

- Session mode/source/metrics/counters can be derived from accepted completed results.
- Recommendations, evidence opportunities, weakness identities, state transitions and offered actions can be derived from accepted profile/mastery code.
- Action **selected** must be captured at the explicit start boundary in a future consented study; it cannot be inferred from an offer snapshot.
- Public catalog references require an allowlist. Private custom/quote target identities should be omitted or mapped locally to opaque study references; hashing a rare private word alone does not guarantee anonymity.
- Collect the minimum study evidence, obtain consent, define retention/deletion and local pseudonym rotation, and validate the export before adding a transport. Consent/export/retention/transport are not implemented here.
- Stable session sequence and dedupe IDs exist; localStorage still provides no cross-tab transaction or cloud synchronization guarantee.

Slice 9 planner readiness was conditional on generator dead ends and category crowding. Slice 10 addresses those engineering blockers; the current readiness decision is in [SLICE10.md](SLICE10.md). Finite bank reuse needs scheduling controls and human language review. Actual user histories are required to calibrate detection, training/transfer latency, controlled wait/check counts and regression sensitivity. Slice 9 itself introduces no policy changes.

## Slice 10 report additions

`slice9-baseline.json` freezes accepted counts and all three original starvation traces, captured from the accepted source before implementation. It includes uncapped original eligible lists, raw scores, records and visible actions. The evaluator JSON embeds that baseline and current full audits under `robustness`; no production UI imports this fixture. `FINDINGS.md` is preserved byte-for-byte.

The unchanged 1,568-attempt matrix distinguishes generated, unsupported, and supported failures by focus/type/level/purpose/reason. An additional 256-attempt stress matrix covers both repaired focuses, all ordinals and two more learner scopes, comparing capability witnesses with direct generation. Performance JSON separately reports those runtimes and recommendation selection over actual histories and the largest actual eligible list. Profile-limit selection stress also exercises 306 candidates in unit tests.

Capability answers apply to the exact content-bank object/version, focus, scope, progression level, purpose and ordinal. A successful preflight returns an independently verified immutable exercise witness; it does not reserve a variant, create a session or claim all possible future ordinals are supported. Curated-resource gaps produce an ordinary-practice action before any controlled check is offered. Unicode training drills remain supported; drill-only content cannot establish a controlled assessment.
