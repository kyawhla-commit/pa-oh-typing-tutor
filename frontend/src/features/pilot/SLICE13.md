## 4. Pilot architecture

A local facilitator page owns a bounded recorder and validated storage. A separate iframe renders existing Practice/Test in its own React/service realm, with study-only providers and synthetic scope ownership. It reports read-only lifecycle/outcome milestones via same-origin messages. The parent rejects unknown envelope fields, wrong origin/window/participant/task/epoch and validates every milestone. Fresh fixture/reset epochs prevent stale frame capture and stale service caches. No analytics SDK or server collector.

The only shared extensions are context exports and optional typing lifecycle observer registration. Existing input subscriptions, engine, scoring, accepted completion and planned outcome behavior are unchanged. Narrow color corrections address measured contrast in passage text and small typing labels/hints. Study mode removes remote fonts and disables Supabase initialization; production styling/font loading and normal account behavior otherwise remain intact.

## 6. Consent flow

Read the concise voluntary product-test script in [PROTOCOL.md](PROTOCOL.md). Participation may be paused/stopped/skipped at any time, without academic/medical assessment or hidden recording. Participation consent gates capture. Notes/quotes and each audio/video/screen permission are separate. This tool records no media. Agree local access/retention/deletion terms before a real session. Default provenance is engineering rehearsal; changing it to consented-pilot does not itself prove human participation.

## 7. Pseudonyms

P01–P99 only; invalid names/email-like identifiers are rejected. No account sign-in, real email/name or custom text entry is used. Learning scopes are `user:study-v1:<pseudonym>:<epoch>`; a fixed generic in-memory learner enables the existing scope API. Observation keys are per pseudonym, and frame epochs are validated.

## 8. Local events

Twelve compact milestone types cover task start, offered recommendation, activity start/skip/cancel/completion/known abandonment, check start/completion, navigation, fixture load and facilitator note. Each has pseudonym, sequence, task and nondecreasing relative time. Optional metadata is coarse action/recommendation/level/state, hashed source/version, route or fixture ID. Accepted completions include mode, correct WPM, attempt accuracy, attempts, errors, corrected errors and completion reason. No per-character logging.

## 9. Manual observations

Success / success-with-help / failed / abandoned, ten predefined confusion tags, wrong clicks, help-needed, explanation accuracy and optional reviewed note. Notes are manual and require separate permission; no inferred emotion or confusion. Task results are independent of learning/mastery outcomes. Count one latest final observation per participant/task, retaining earlier attempts as context and marking missing tasks.

## 10. Privacy protections

Strict deep whitelists reject raw buffer/passage/ledger/mistake replay, email/credential fields, unknown nested metrics and identifying source IDs. Source/version references are opaque hashes. Notes are capped at 500 characters; obvious email/IP/URL/credential patterns are rejected and facilitator review is required. This scanner cannot recognize every personal name or private quote. No localStorage dump, auth token or absolute timing is exported.

Study HTML restricts script/style/font/connect destinations with CSP, and a mode-only Vite transform removes the shared Google Fonts import. The checked study workspace sent **zero remote requests**. Data stays local; storage is not encrypted and local export access/retention remains the facilitator’s responsibility.

## 16. Think-aloud

Use “What are you thinking?”, “What do you expect this button to do?”, “What does this message mean to you?” and “What would you do next?” Wait before intervening; record help. Avoid suggestions naming the answer or leading satisfaction questions.

## 17. Predefined criteria

Scripts and fixed criteria exist in `tasks.ts`, the protocol and exports before participant data. They cover locating/starting, explaining the reason, declining without perceived penalty, distinguishing Cancel, recognizing composition differences, check comprehension, optional support and recovery/next action. Code help separately; do not move goalposts. Use descriptive counts and themes, not significance/efficacy or misleading tiny-sample averages.

## 18. Usability severity
